# 1.19.0 – vorhandene Geräte, verlässlicher Zustand

Diese Erweiterung nutzt vorhandene HCU-Geräte und bestehende Shelly-Cacheeinträge.
Neue Gerätesysteme, automatische Alarmquittierung und Hausautomationen sind nicht
Teil des Updates. Die Connect API 1.0.1 ist die Grundlage der HCU-Payloads.

## Bedienung und HTTP

Neue Seiten: `/controls` (Licht/Rollläden), `/security` (nur lesend), `/energy`
(optionale Historie), `/diagnostics` (geheimnisfreie JSON-Diagnose). Die Heizung
steuert jetzt tatsächlich Gruppen-Sollwert, MANUAL/AUTOMATIC und Boost.
Browserbefehle benötigen Anmeldung und CSRF-Token. Externe Befehle verwenden
`POST`, JSON und `X-API-Key` entsprechend der API-Konfiguration.

```http
POST /hmipShutter
X-API-Key: <api-key>
Content-Type: application/json

{"device":"<BROLL-device-id>","channelIndex":1,"action":"position","level":32}
```

Stop: `{"device":"<device-id>","channelIndex":1,"action":"stop"}`.
Nur `SHUTTER_CHANNEL` ist zulässig. `level` 0–100 wird unverändert auf HCU
`shutterLevel` 0–1 abgebildet; keine zusätzliche Invertierung und kein Versprechen
„0 = offen“. Die Position folgt der HCU-Referenzfahrzeit, nicht einer Höhenmessung.

```json
// POST /hmipHeating, jeweils eine Aktion
{"group":"<HEATING-group-id>","action":"temperature","temperature":21}
{"group":"<HEATING-group-id>","action":"mode","mode":"AUTOMATIC"}
{"group":"<HEATING-group-id>","action":"boost","boost":true}

// POST /hmipLight, dimLevel und saturation in Prozent
{"device":"<device-id>","channelIndex":1,"action":"dim","dimLevel":40}
{"device":"<device-id>","channelIndex":1,"action":"rgb","hue":120,"saturation":80,"dimLevel":40}
{"device":"<device-id>","channelIndex":1,"action":"scene","sceneId":1,"dimLevel":40}
{"group":"<switching-group-id>","action":"rgb","hue":120,"saturation":80,"dimLevel":40}
```

Die Kommentare gehören nicht zum übertragenen JSON. Temperaturgrenzen und
`controllable`/`boostAllowed` werden aus dem aktuellen Snapshot geprüft. ECO ist
kein zulässiger Wert für den verwendeten HCU-Aufruf `setControlMode`.
RGB-Farbton: ganze Zahl 0–359; Szenen-ID: vorhandene HCU-Szenen-ID.
Eine Farbtemperatur-Aktion (`action: "temperature"`, `colorTemperature` in Kelvin)
wird ausschließlich bei expliziter Kanalfähigkeit angeboten. RGB/RGBW-Produktnamen
oder leere Temperaturfelder allein reichen nicht; `channelActive` beschreibt
Aktivität und darf einen eingerichteten Lichtkanal nicht ausblenden.

Lichtgruppen müssen normale Schaltgruppen mit passenden konfigurierten Kanälen
sein; Alarmgruppen sind ausgeschlossen. Gruppen-RGB nutzt wegen eines
widersprüchlichen Gruppenbeispiels in der Dokumentation einzelne dokumentierte
Geräteaufrufe. Jede Antwort wird geprüft; ein Fehler stoppt die Serie und meldet
bereits bestätigte Teilbefehle. Kein Rollback-Versprechen für Geräteaktionen.

Erfolg bedeutet HCU-Bestätigung, nicht unabhängige Bestätigung der physischen
Wirkung. Verbindungsfehler: 503; Ablehnung: 502; Antwort-Timeout: 504. Es gibt
keinen HTTP-Endpunkt für beliebige HCU-Pfade. Bestehende Endpunkte bleiben bestehen.

## Loxone

Beim ersten gültigen Vollsnapshot jeder Verbindung, standardmäßig alle 300
Sekunden und auf `POST /api/loxone/resync` wird der aktuelle Vollzustand versendet.
Die Dashboard-Schaltfläche verwendet einen separaten Session-/CSRF-Endpunkt.
`loxone.resync_interval_seconds: 0` deaktiviert nur die periodische Wiederholung.
Es wird der lokal vorhandene Snapshot übertragen, kein zusätzlicher Steuerbefehl.
UDP hat keine Empfangsbestätigung: API-Erfolg heißt „gesendet“, nicht „zugestellt“.

Format bleibt `NAME@WERT\r\n`, mehrere ganze Zeilen pro begrenztem UDP-Datagramm.
Werte fehlen bei unbekanntem Zustand statt einen sicheren Zustand vorzutäuschen.

| Daten | Variablenmuster |
| --- | --- |
| Gerät/Kanal | `hmip_<ID>_ch<N>_<field>` |
| Gerät verfügbar | `hmip_<ID>_available` |
| Gruppen | `hmip_group_<ID>_<field>` |
| Home | `hmip_home_<field>` |
| Wetter | `hmip_home_weather_<field>` |
| Sicherheit | `hmip_home_security_<field>` |
| Sicherheitszonen-Zuordnung | `hmip_home_security_zone_<ZONE>_groupId` |
| Shelly-Energie | `shelly_<SOURCE_ID>_ch<N>_power_w`, `_import_kwh`, `_export_kwh` |

`SECURITY_ZONE.active` beschreibt Scharfschaltung. `SecurityFunctionalHome.active`
beschreibt dagegen die Aktivierung der Lösung, nicht „scharf“. Alarmzustand wird
separat gezeigt. DEVICE/GROUP_REMOVED setzt Verfügbarkeit auf 0; Empfänger sollten
gespeicherte Kanalwerte mit dieser Verfügbarkeit verknüpfen. Nicht jeder API-Wert
wird ungefiltert übertragen; allowlists, endliche Zahlen und sichere IDs verhindern
Format-Injektionen. Einzelne Schlüssel stehen in `app/loxone_udp.py`.

## Energie – explizites Opt-in

```yaml
energy:
  enabled: false
  interval_seconds: 60
  retention_days: 90
  timezone: Europe/Berlin
```

Aktivieren auf `/energy` speichert die Auswahl separat in `config/energy.yaml`,
ohne die HCU-Konfiguration zu ersetzen. Beide Dateien bleiben privat, ebenso
`data/energy.sqlite3`. Bereits vorhandene erreichbare Gen1-Shelly-Zähler werden
nur gelesen: keine neuen Scans, Relaisaktionen, Firmware- oder Messkonfiguration.
Die Historie unterstützt meter/emeter, stabile Quellen-IDs und mehrere Messkanäle.
Offline-Cacheeinträge sind keine Voraussetzung. Der Dienst hat einen eigenen
Stop-Mechanismus und kann die Bridge nicht versehentlich global beenden.

Die erste Messung bildet eine Baseline. Summen folgen Zählerdifferenzen, nicht
ungeprüfter Integration von Leistung. Import und Export werden unabhängig geprüft;
Rücksetzungen, ungültige/fehlende Messungen und Messlücken werden berücksichtigt.
Intervalle über Mitternacht werden dem Ende zugeordnet und als Näherung markiert.
Tages-/Monatssummen sind keine abrechnungsgeeichten Werte. Aufbewahrung bezieht
sich auf lokale Kalendertage; die Baseline bleibt auch nach Bereinigung erhalten.
Deaktivieren löscht die bisherige Datenbank nicht. `GET /api/energy` ist geschützt.

## Betrieb und Fehlerbehebung

`GET /api/diagnostics` zeigt Version/Build-Commit, Verbindung/Readiness,
Geräte-/Gruppenanzahl sowie optionale Dienstzustände. Keine Tokens, Passwörter,
Rohsnapshots oder vollständige Konfiguration. Docker kann den Build-Commit über
`--build-arg BRIDGE_BUILD_SHA=<commit>` einbetten; sonst steht dort `unknown`.

Das Update enthält außerdem: HCU-ACK-Korrelation, Snapshot-Recovery, lesende
Liveness-Prüfung mit Antwortfrist, korrektes Health ohne mtime-Fehlalarm,
kontrollierten Config-Reconnect, strikte Payloadvalidierung, graceful Shutdown,
Shelly-Digest-Authentifizierung/tatsächliche Switch-IDs und Cache-Löschen/Neueinlesen.
Der externe Shelly-Relaisendpunkt ist separat API-Key-geschützt.

Vor einem Update Code/Config/Daten und bisheriges Docker-Image sichern. Bestehende
Config, Zertifikat, API-Key und Passwortdateien nicht durch Vorlagen ersetzen.
Das Config-Verzeichnis wird für atomare Schreibvorgänge gemountet; das Zertifikat
separat read-only. Ein Config-Dateimount verhindert sonst atomare Updates.
`restart: unless-stopped` startet einen lediglich `unhealthy` markierten Container
nicht automatisch neu; die WebSocket-Recovery läuft innerhalb der Anwendung.

Alle automatisierten Gerätebefehle werden mit gemocktem Versand geprüft. Ein
realer Rollladen-/Heiz-/Licht-/Sirenenfunktionstest muss separat und bewusst
durchgeführt werden. Dieses Update aktiviert keine Sirene und keine Energiehistorie.
