# 1.21.0 – Loxone-taugliche Werte, robustere Steuerung, Nur-Lese-Key

Umsetzung der Vorschläge aus dem Loxone-Abgleich. Alle Zusätze sind per
`config.yaml` abschaltbar; das bisherige UDP-Format bleibt unverändert erhalten,
neue Variablen kommen nur hinzu.

## 1. Mehr Werte für Loxone (UDP)

| Variable | Werte | Quelle |
|---|---|---|
| `hmip_<ID>_ch<N>_windowOpen` | 0 = zu, 1 = offen, 2 = gekippt | `windowState` |
| `hmip_<ID>_ch<N>_smokeAlarm` | 0/1 (alles außer `IDLE_OFF` = 1) | `smokeDetectorAlarmType` |
| `hmip_group_<ID>_controlModeManual` | 0/1 | `controlMode` |
| `hmip_home_climate_absenceActive` | 0/1 (alles außer `NOT_ABSENT`) | `absenceType` |
| `hmip_home_weather_weatherConditionCode` | 0 CLEAR … 13 STRONG_WIND (Liste in `app/loxone_udp.py`) | `weatherCondition` |
| `<…>_dimLevelPct`, `shutterLevelPct`, `slatsLevelPct`, `valvePositionPct`, `saturationLevelPct` | 0..100 | 0..1-Felder |
| `hmip_home_deviceCount`, `unreachCount`, `lowBatCount`, `sabotageCount` | Anzahl | alle Geräte |
| `bridge_heartbeat` | zählt hoch (alle `heartbeat_interval_seconds`) | Bridge |
| `bridge_hcuConnected` | 0/1 | Bridge |

Die Sammelwerte gehen beim Vollsync und nach jedem HCU-Event raus, wenn sich ein
Zähler geändert hat. `bridge_heartbeat` am Virtuellen UDP-Eingang mit
Empfangs-Zeitüberschreitung überwachen, dann merkt Loxone einen Bridge-Ausfall.

Schalter: `loxone.numeric_states`, `loxone.percent_values`, `loxone.aggregates`,
`loxone.heartbeat_interval_seconds` (0 = aus).

## 2. Steuerung

- **Funk-Schutz** (`command_guard`): identische Befehle innerhalb von
  `dedupe_window_ms` (500) werden nicht erneut gefunkt (`request_id`
  `duplicate:<rid>`). Pro Gerät/Gruppe mindestens `min_interval_ms` (150) Abstand;
  kommt währenddessen ein neuerer Befehl derselben Art für denselben Kanal, gewinnt
  er (`superseded:`), z.B. bei Dimm-Rampen. Ab `duty_cycle_limit_percent` (80,
  Home-Duty-Cycle der HCU) wird alles außer Alarm/Sirene mit **429** und
  `Retry-After: 60` abgelehnt.
- **Rückmeldung an Loxone** (`loxone.command_feedback`): nach jedem Befehl
  `hmip_<ID>_lastCmdOk` (0/1) und `hmip_<ID>_lastCmdCode` (HTTP-Status, z.B. 409
  „Lichtfunktion nicht konfiguriert“, 429 Duty Cycle, 504 keine HCU-Antwort);
  bei Gruppen `hmip_group_<ID>_…`.
- **RGB im Loxone-Format**: `/hmipRGB` nimmt `"rgb"` zusätzlich als Zahl
  `BBBGGGRRR` (je 0..100 %) direkt vom Lichtsteuerungs-Ausgang, z.B.
  `{"device":"<id>","rgb":<v>}`. Lumitech-Werte `20BBBTTTT` (Helligkeit +
  Kelvin) werden als Farbtemperatur gesetzt. 0 schaltet aus.
- **Räume und Namen statt IDs**: `"label"` (+ optional `"room"`) für
  Geräte-Endpunkte (`/hmipSwitch`, `/hmipDimmer`, `/hmipRGB`, `/hmipIrrigation`,
  `/hmipShutter`, `/hmipLight`), `"groupLabel"` für Gruppen (`/hmipThermostat`,
  `/hmipHeating`, `/hmipAlarm`, `/hmipLight`), bei Heizung auch nur `"room"`.
  Mehrdeutig → 409 mit Kandidaten, unbekannt → 404. Eine ID hat immer Vorrang.

```json
{"label": "Deckenlicht", "room": "Wohnzimmer 2OG", "on": true}
{"room": "Bad", "action": "temperature", "temperature": 21.5}
```

## 3. Einrichtung in Loxone

- **Vorlage**: `GET /api/loxone/template.xml` liefert einen Virtuellen
  UDP-Eingang (`VirtualInUdp`) mit allen gesendeten Zahl/Ja-Nein-Variablen,
  Befehlserkennung `…@\v`, Digital/Analog und Einheit. Filter wie beim Mapping
  (`room`, `entity`, `field`, `target`, `kind`), dazu `title`, `address`.
  Datei in Loxone Config als Vorlage importieren.
- **Auswahl** (`loxone.filter`): `groups`, `diagnostics`, `include_/exclude_fields`,
  `include_/exclude_rooms`, `include_/exclude_devices` (ID oder Label). Gilt für
  Push, Vollsync und Rückmeldungen; `bridge_*` wird immer gesendet.
  `/api/loxone/mapping` zeigt pro Variable `sent`.
- `/api/loxone/mapping` kann filtern und blättern: `room`, `entity`, `field`
  (kommagetrennt), `target`, `kind`, `sent=1`, `offset`, `limit`. Neu je Eintrag:
  `unit`, `sent`, Antwort mit `total`.

## 4. Sicherheit

- **Nur-Lese-Key**: wird beim Start als `data/api_key_readonly.txt` erzeugt
  (oder `api_key_readonly` / ENV `BRIDGE_API_KEY_READONLY`). Er gilt für
  `/api/inventory`, `/api/loxone/mapping`, `/api/loxone/template.xml`,
  `/api/diagnostics`, `/api/security`, `/api/energy`, `/hmipState` – nicht für
  Steuerbefehle (401). Der Haupt-Key funktioniert weiterhin überall.
  API-Keys werden jetzt zeitkonstant verglichen.
- **IP-Freigabe**: `control_allowed_ips` (IPs/Netze) beschränkt alle
  Steuerbefehle auf diese Absender (sonst 403); Lesen bleibt erlaubt.
- **HTTPS**: Waitress spricht kein TLS. Für verschlüsselte Übertragung einen
  Reverse-Proxy (z.B. Caddy/nginx) vorschalten; `control_allowed_ips` sieht
  dann die Proxy-Adresse.

## 5. MCP-Server und Betrieb

- Installierbares Paket unter `mcp-server/`, Startbefehl `homematic-bridge-mcp`:

  ```
  pipx install "git+https://github.com/derzico/homematic-bridge.git#subdirectory=mcp-server"
  ```

  Update: `pipx upgrade homematic-bridge-mcp` bzw. `pipx install --force …`.
  `ops/mcp_server.py` bleibt als Kompatibilitätsstart erhalten.
- Neue Tools `hmip_summary` (kleiner Überblick) und `hmip_loxone_template`.
  `hmip_loxone_mapping` filtert serverseitig und liefert standardmäßig 100
  Einträge kompakt; `hmip_inventory` filtert nach Raum/Typ/Gerät, blättert und
  lässt Loxone-Variablen standardmäßig weg.
- UTF-8 wird im Skript selbst gesetzt (kein `-X utf8` unter Windows nötig).
- Für den MCP den Nur-Lese-Key verwenden (`BRIDGE_API_KEY_FILE` →
  `data/api_key_readonly.txt` bzw. Kopie davon).

```json
"homematic-bridge": {
  "command": "homematic-bridge-mcp",
  "env": {"BRIDGE_URL": "http://<bridge-ip>:8080",
          "BRIDGE_API_KEY_FILE": "<pfad>/api_key_readonly.txt"}
}
```

- **Build-Kennung**: `ops/deploy.sh` (git pull mit Erhalt der lokalen
  `internal_config.yaml`, Build mit `BRIDGE_BUILD_SHA`, Healthcheck);
  `/api/diagnostics` zeigt `build_commit`, Heartbeat-Zähler, Filterstatus und
  Sicherheitsstatus.
